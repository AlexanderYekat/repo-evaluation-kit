# Форматы входа и доказательств

Эти форматы используются [скриптом](../scripts/kit.py), [шаблонами](../assets/) и методикой исследования. JSON хранится в UTF-8. Повторяющиеся ключи JSON запрещены. Поля реестров обязательны; неизвестное обозначается `null`, пустым массивом или определённым ниже статусом, а не вымышленным значением. Даты — ISO 8601. Идентификаторы состоят из латинских букв, цифр, `_` и `-` и уникальны внутри своего реестра.

## request.json

Источник истины для ключей, типов и допустимых значений — [request.schema.json](../assets/request.schema.json). [Минимальный пример](../assets/request.minimal.json) содержит условные адреса `example`, а не результаты исследования.

Обязательны только `goal` (непустой текст) и `repositories` (непустой массив URL). URL репозитория: `http://`, `https://` или `ssh://`, без имени пользователя/пароля, query и fragment; scp-форма `git@host:path` не поддерживается. Дубликаты допустимы и сохраняются как отдельные входные позиции.

Необязательные строки: `project_name`, `project_id`, `current_state`, `environment`. `project_id` — безопасное имя каталога: до 80 латинских букв/цифр, `_`, `-`, первая позиция — буква или цифра; зарезервированные Windows-имена запрещены при создании каталога. Необязательные массивы строк: `decisions`, `avoid_building`, `constraints`, `scenarios`, `success_criteria`. Отсутствующий контекст остаётся неизвестным.

`depth`: `overview` (по умолчанию), `deep-static`, `execution`. `permissions` содержит только булевы `fetch_sources`, `install_dependencies`, `build`, `run_tests`, `start_services`. Отсутствующие разрешения означают `false`. Глубина `execution` сама по себе не выдаёт разрешений. Чтение доступных документов и страниц исходников остаётся статической работой; загрузка/клонирование исходников учитывает `fetch_sources` и ограничения среды. Разрешения не заменяют границы безопасности среды и ранее данные пользователем указания.

Скрипт проверяет именно подмножество JSON Schema, используемое поставляемой схемой; сторонний JSON Schema-пакет не требуется. `format: uri` дополнительно проверяется стандартным парсером URL. Неизвестные поля и неверные типы отвергаются, включая строки вместо булевых значений. Сохранённый `request.json` сохраняет вход без автоматического добавления выводов или предположений.

## INVENTORY.json

Корень: `schema_version: "1.0"`, `input_count` (число входных ссылок, включая повторы), `repositories` (массив в исходном порядке). Каждая запись содержит:

- `id`: `r01`, `r02`, …; `input_index`: позиция с 1; `input_url`: исходная ссылка без подмены.
- `canonical_url`: подтверждённая каноническая ссылка или `null`. Нормализация не должна молча превращать форк в upstream.
- `access`: `NOT_CHECKED`, `AVAILABLE`, `UNAVAILABLE`; `access_reason`: основание статуса, всегда непустая строка. Недоступность не означает бесполезность.
- `default_branch`: имя ветки или `null`; `commit`: полный SHA репозитория из 40 или 64 hex-символов либо `null`; `commit_source`: URL, подтверждающий commit, либо `null`. SHA blob/файла не является commit репозитория. Валидатор проверяет форму и наличие ссылки, содержательную подлинность проверяет исследователь.
- `origin`: объект с `kind` (`UNKNOWN`, `ORIGINAL`, `FORK`), `upstream_url` (URL или `null`), `comparison` (`NOT_CHECKED`, `CHECKED`, `NOT_APPLICABLE`). Для `FORK` нельзя выбирать `NOT_APPLICABLE`; неизвестный upstream допускается с `NOT_CHECKED` и предупреждением. Неизвестное происхождение требует `NOT_CHECKED`; `CHECKED` требует известного upstream. Чтение upstream не доказывает свойства форка.
- `project_type`: строка или `null`; `roles`: массив ролей относительно цели; `priority`: объясняющая строка или `null`.
- `scope`: `PENDING`, `OVERVIEW`, `DEEP_STATIC`; результат запусков записывается отдельно и не превращает обзор автоматически в глубокий аудит.
- `duplicate_of`: идентификатор более ранней записи или `null`. Точный повтор входной ссылки скрипт отмечает автоматически. Разные URL одного проекта связывает исследователь после проверки идентичности.
- `report`: обязательно `reports/r01.md` для `r01` и аналогично для остальных. Карточка создаётся и для дубликата, и для недоступного кандидата.

## EVIDENCE.json

Корень: `schema_version: "1.0"`, массивы `sources`, `claims`, `runs`. Пустой реестр допустим для заготовки с предупреждением о незавершённости. Не заполняйте его предположениями ради прохождения валидатора.

### sources — прочитанные основания

Каждая запись содержит ровно `id`, `repository_id`, `kind`, `commit`, `url`, `path`, `lines`, `captured_at`, `note`.

- `id`: например `s01-readme`; `repository_id`: существующий ID из inventory.
- `kind`: `DOCUMENTATION`, `SOURCE`, `METADATA`.
- `commit`: полный SHA, совпадающий с inventory, или `null`. Для `SOURCE` без доступного Git commit обязательна причина в `note`; валидатор предупреждает о незакреплённой версии. Это ограниченное наблюдение исходников, которое нельзя переносить на произвольную версию.
- `url`: URL источника без credentials или `null`. Для источников допустимы query/fragment, в частности `#L10-L25`.
- `path`: путь файла внутри исследуемого репозитория с `/` или `null`; это координата исходника, файл не обязан быть скачан. Абсолютные пути и выход через `..` запрещены.
- `lines`: `[начальная, конечная]`, включительно, положительные целые, или `null`. Для `SOURCE` обязательны `path` и `lines`.
- `captured_at`: дата или дата-время фактического чтения, например `2026-09-16`; `note`: строка с контекстом чтения и ограничениями, может быть пустой.

Для `METADATA` обязателен URL и дата чтения. Для документации допустимы URL/дата либо path/lines; неприкреплённая к commit документация вызывает предупреждение. Не приписывайте такому источнику свойства конкретной версии кода. URL без реального чтения не становится доказательством. Можно записывать path/lines без URL для разрешённого локального исследования; отсутствие доступного commit обозначайте явно.

### claims — существенные утверждения

Каждая запись содержит ровно `id`, `repository_id`, `status`, `statement`, `source_ids`, `run_ids`, `limitations`.

`statement` — непустой проверяемый вывод, `limitations` — строка с областью применимости. `source_ids` и `run_ids` — массивы уникальных ссылок на основания того же репозитория. Для межрепозиторного синтеза ссылайтесь в отчёте на несколько отдельных утверждений.

- `DOCUMENTATION`: авторское заявление; нужна хотя бы одна ссылка на `DOCUMENTATION`.
- `SOURCE`: найденная реализация в определённых файлах; нужна ссылка на `SOURCE`. Наличие кода не доказывает его выполнение.
- `RUN`: подтверждённое поведение в условиях запуска; нужны ссылки на выполненные `PASS` или `FAIL` с реальными assertions. Наблюдаемая ошибка может подтвердить дефект в проверенных условиях; для `FAIL` обязательно раскрыть эти условия в `limitations`. Сбой подготовки с нулём проверок нельзя выдавать за подтверждение поведения приложения.
- `INFERENCE`: вывод исследователя; обязательно основание в `source_ids` или `run_ids` и непустые ограничения. Неудачный запуск можно использовать как основание ограниченного вывода с указанием условий.
- `UNKNOWN`: не установлено; обязательна причина в `limitations`, основания могут отсутствовать.

Документированное обещание, которое пока не найдено в просмотренном коде, остаётся `DOCUMENTATION`; отдельный `UNKNOWN` или ограниченный `INFERENCE` фиксирует границу поиска. Нельзя превращать это в утверждение об отсутствии реализации во всём проекте.

### runs — проверки выполнения

Каждая запись содержит ровно `id`, `repository_id`, `commit`, `status`, `kind`, `command`, `environment`, `expected`, `result`, `log`, `tests`, `assertions`, `skipped`, `mocks_only`, `reason`.

- `status`: `PASS`, `FAIL`, `NOT_RUN`, `BLOCKED`. `kind`: `BUILD`, `TEST`, `INTEGRATION`, `BENCHMARK`, `OTHER`.
- `command`, `environment`, `expected`, `result`: непустые строки для выполненного запуска, иначе строка или `null`. Окружение включает релевантные версии и условия, результат — наблюдение, а не только код завершения процесса.
- `log`: существующий файл относительно каталога исследования с `/`, для выполненного запуска обязателен. Сохраняйте вывод с предварительным удалением секретов.
- `commit`: для `PASS`/`FAIL` обязателен и совпадает с inventory; иначе допустим `null`.
- `tests`: количество **реально выполненных** тестов, исключая пропуски; `assertions`: число реально выполненных проверок результата; `skipped`: число пропущенных тестов. Все три — неотрицательные целые.
- `mocks_only`: булево; `reason`: причина `NOT_RUN`/`BLOCKED`, в остальных случаях строка или `null`.

`PASS` требует `assertions > 0`; для `TEST`/`INTEGRATION` также `tests > 0`. Для `BUILD` учитывайте реальные проверки ожидаемых артефактов/результата сборки; такой PASS не подтверждает поведение приложения. Пропуски не входят в `tests`: skipped-only набор имеет `tests: 0` и не проходит как PASS. `INTEGRATION` с `mocks_only: true` отвергается как доказательство реальной интеграции. Допустимо честно записать успешный unit-тест с mocks, не называя его интеграционным.

`NOT_RUN`/`BLOCKED` требуют причины, нулевых счётчиков, `result: null`, `log: null`, `mocks_only: false`. Заготовка сценария может содержать будущую команду, ожидаемый результат и плановое окружение, но не наблюдаемый результат или журнал якобы выполненного запуска. `FAIL` фиксирует выполненную проверку с несоответствием; отсутствие assert или сбой до тестов не требуется маскировать положительным результатом.

Валидатор проверяет взаимосвязи и декларации счётчиков. Он не исполняет код, не читает чужие тесты, не доказывает истинность записанного числа assertions и не распознаёт скрытые mocks. Это предмет ревью логов, тестов, области проверки и реального пути данных.

## Команды и ограничения механики

Из каталога комплекта (в Windows достаточно `.\new-project.cmd имя-проекта`;
вместо `python` можно `py -3`):

```text
.\new-project.cmd notes-search
python .agents/skills/repo-evaluation/scripts/kit.py new-project notes-search
python .agents/skills/repo-evaluation/scripts/kit.py new-project notes-search --parent D:/Projects
python .agents/skills/repo-evaluation/scripts/kit.py validate-request request.json
python .agents/skills/repo-evaluation/scripts/kit.py init --request request.json --project notes --run first
python .agents/skills/repo-evaluation/scripts/kit.py init --request request.json --output /allowed/location/new-run
python .agents/skills/repo-evaluation/scripts/kit.py check-run evaluations/notes/first
python .agents/skills/repo-evaluation/scripts/kit.py check-kit .
python .agents/skills/repo-evaluation/scripts/kit.py new-project --output /allowed/location/research-project
python .agents/skills/repo-evaluation/scripts/kit.py new-project --output . --adopt --reset-git
```

Без `--output` назначение — `evaluations/<project-id>/<run-id>` относительно текущего каталога; `project_id` берётся из `--project`, входа или `project`, run-id из `--run` или UTC timestamp. `--output` нельзя совмещать с `--project`/`--run`. Имя проекта для отображения берётся из контекста; `project_name` не используется для построения путей.

`init` всегда отказывается от существующего назначения и дерева самого skill; в checkout комплекта также защищены существующие каталоги образца, исходников и шаблонов. Обычные имена внешних каталогов вроде `sources` сами по себе не запрещены. Он не загружает репозитории, не запускает команды из них, не ставит зависимости и не заполняет содержательные выводы. Процесс соблюдает права ОС/среды; внешний каталог допустим только в пределах разрешений. Ошибка записи оставляет незавершённое новое назначение для осмотра, автоматического удаления нет.

`new-project` (то же, что `new-workspace`) создаёт отдельный проект исследования:
достаточно имени папки. По умолчанию это `C:\MyProjects\<имя>` в Windows, иначе
`~/MyProjects/<имя>`; каталог создаётся при необходимости. Другой корень: `--parent`
или переменная `REPO_EVALUATION_PROJECTS_DIR`. `--output` задаёт полный путь и не
совмещается с именем. Цель и ссылки на этом шаге не требуются. Копируются skill,
промпты комплекта если они рядом, рабочий README/AGENTS, gitignore, в котором
`evaluations/` версионируется, а checkout'ы кандидатов нет, и пустой `git init` без
commit и remote. Не копирует `.git`, `tests/` и результаты комплекта. Назначение не
должно существовать и не может лежать внутри skill. `--adopt` переводит уже
скопированную папку комплекта: всегда обновляет `.gitignore`, при первом переводе
пишет README/AGENTS и `workspace.json`, не трогает уже начатые `evaluations/`.
`--reset-git` удаляет `.git` и делает новый `git init`; для каталога
`repo-evaluation-kit` нужен `--force`. Commit не создаётся.

`check-run` проверяет количество и порядок входов, карточки, допустимые поля и статусы, совпадение commits, ссылки между реестрами, обязательные данные запуска и существование локальных Markdown-ссылок. Исходники в `sources/` не исполняются и не проверяются как документы комплекта. `check-kit` проверяет переносимую границу skill, минимальный вход и локальные ссылки, пропуская неизменяемый образец, результаты в `evaluations/`, кеши и скачанные исходники. Ссылки шаблонов на будущие файлы проверяются после `init` через `check-run`. Якоря разделов Markdown и удалённые URL механически не проверяются.

Код возврата `0` означает структурную согласованность, включая честную незавершённую заготовку с предупреждениями. Код `1` означает ошибку данных/файлов. Пройдённая проверка структуры не означает завершённый или достоверный аудит.
